⚠️ **AXIOM strings are UTF-8 by default**, and the language is to **support other string types** as well (user directive 2026-07-10; spec `01.minimal core.md` names "String thao tác chuỗi UTF-8" as a stdlib goal).

**Implications for any string work:**
- `for c in s` over the default `str` must yield **UTF-8 codepoints (runes)**, NOT raw bytes. A byte-by-byte loop splits multi-byte codepoints → wrong. (I was about to ship byte-based for-in-string and stopped — it would be incorrect.)
- The element type of iteration/`s[i]` is a design question: codepoint = `u32`/rune? grapheme? Current `s[i]` returns a **byte** (type 5), and `s.len` is the **byte** length — these are byte-level primitives, fine for ASCII/byte ops but NOT codepoint iteration.
- Current reality: `TYPE_STRING` (id 12) is a single `{ptr: ptr[u8], len: i64}` byte buffer (16-byte INLINE primitive, the sharp-edge ABI area [[bug77-16byte-struct-byaddress-unified]]). There is **no multi-string-type system implemented yet** — UTF-8/other-encodings is design intent.

**Task deferred:** `for c in <str>` iteration (RFC 0018 P2-future) needs a UTF-8-aware design first (codepoint decode in `lower_for`, chosen element type, and how "other string types" select byte vs codepoint iteration). This is an RFC/design decision — do NOT ship byte iteration as a shortcut. Array + Vec[T] iteration already shipped [[rfc0018-for-in-array-shipped]].
